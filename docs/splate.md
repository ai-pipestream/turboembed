# Sparse Late Interaction (`SPLATE`) Four-Arm Cascade Harness (Part of `#711`)

This document describes the four-arm **Sparse Late Interaction (SPLATE)** (Formal et al., [arXiv:2404.13950](https://arxiv.org/abs/2404.13950)) evaluation harness in `turbo-eval` (`analysis/eval/src/splate/`), together with its synthetic mechanism benchmark receipt across BEIR subsets and a controlled morphological mismatch corpus.

Per the issue specification, no new public library API is introduced on any published crate; `SparsePostingIndex` (with MaxScore upper-bound pruning), `SplateAdapter`, `CrossEncoderScorer` (including `BundleCrossEncoder` wrapping `turbo::rerank::Reranker`), and the four-arm runner live inside `turbo-eval::splate`.

> [!IMPORTANT]
> **Scope (`Part of #711` -- Synthetic Mechanism Harness)**:
> The benchmark tables in Section 3 are generated by `encode_loaded_set` (`analysis/eval/src/splate/corpus.rs`) and `InteractionCrossEncoder` (`analysis/eval/src/splate/arms.rs`), which construct deterministic seeded word-and-stem representations (`FNV-1a` + LCG coordinates) rather than running trained SPLADE, ColBERT, and cross-encoder neural checkpoints. Accordingly, every table below is labeled as a **synthetic mechanism harness** measuring index sizes, MaxScore posting traversal, SPLATE linear projection (`W t + b` + `MaxLogPool`), and `TokenIndex::rerank` stage costs under controlled representations. Quality conclusions and production architectural recommendations between trained SPLADE, ColBERT, and cross-encoder models are deferred to the follow-up run with pinned trained model bundles via `run_study_with_encoded` and `BundleCrossEncoder`.

## 1. The Four Cascade Arms & Stage Timing Boundaries

All four arms run inside the same process (`analysis/eval/src/splate/`), over identical document, query, and relevance judgment sets (`LoadedSet`), with no implicit query-ID-equals-document-ID self-exclusion (`query` and `doc` IDs are independent namespaces).

To ensure identical timing boundaries across all four arms:
- **`Build (ms)`** (`build_ms`) measures index-structure construction starting from pre-encoded document representations for every arm (`Bm25PostingIndexBuilder` for Arm 1, `IndexBuilder` for Arm 2, and `SparsePostingIndexBuilder` + `TokenIndexBuilder` for Arms 3 and 4, with Arm 4's document `SplateAdapter::encode_tokens` projection completed prior to starting the index-build timer on the same footing as Arm 3).
- **`Encode p50 (us)`** (`encode_p50_us`) measures median per-query representation encoding time from raw query text (Arm 1: BM25 query tokenization; Arm 2: static vector encoding; Arm 3: learned-sparse `MaxLogPool` + token vector encoding; Arm 4: token vector encoding + `SplateAdapter::encode_tokens` vocabulary projection).
- **`Retrieve p50 (us)`** (`retrieve_p50_us`) measures median Stage-1 shortlist retrieval time from the encoded query (`Bm25PostingIndex::top_k`, `VectorIndex::top_k`, or `SparsePostingIndex::top_k`).
- **`Rerank p50 (us)`** (`rerank_p50_us`) measures median Stage-2 reranking time over the top-$C$ shortlist (`0.0` for Arm 1, `CrossEncoderScorer::score_candidates` for Arm 2, and `TokenIndex::rerank` `MaxSim` for Arms 3 and 4).
- **`Search p50 (us)` / `Search p99 (us)`** (`p50_us`, `p99_us`) measure median and tail (`p99`) search latency (`Retrieve + Rerank` from encoded queries) across 5 interleaved rounds (`Arm 1 -> Arm 2 -> Arm 3 -> Arm 4` per query per round).

## 2. Reproduction Commands

All measurements below were collected in `--release` on a single pinned CPU core (`taskset -c 14`), with $d = 32$, $|V| = 2048$, SPLADE/SPLATE document cut `top_k = 64, floor = 0.05`, query cut `top_k = 24, floor = 0.05`, and 5 interleaved timing rounds across shortlist depths $C \in \{10, 25, 50, 100\}$.

To reproduce the exact tables below:

```bash
TURBO_EVAL_CACHE="$TURBO_EVAL_CACHE" \
  taskset -c 14 cargo test --locked --release -p turbo-eval \
  --test splate splate_benchmark_receipt -- --ignored --nocapture
```

To run the unit, parity (MaxScore vs. exhaustive scan, `checked_mul` overflow validation, and shared query/doc ID namespace parity), and sample-dataset integration suite:

```bash
cargo test --locked -p turbo-eval --test splate
```

## 4. Mechanism Observations & Remaining Work for `#711`

1. **Separated Stage Timings (`Encode`, `Retrieve`, `Rerank`, `Build`)**:
   - With document `SplateAdapter::encode_tokens` precomputed prior to `Build (ms)` on the same footing as Arm 3, index construction (`SparsePostingIndexBuilder` + `TokenIndexBuilder`) takes `5.0 to 9.7 ms` on `scifact` (`1,500` docs) and `11.0 to 22.7 ms` on `nfcorpus` (`3,633` docs) across both Arms 3 and 4.
   - Stage-2 `Rerank p50 (us)` (`TokenIndex::rerank` over $C$ candidates) is identical between Arm 3 and Arm 4 (`9.3 us` at $C = 10$, `21.0 vs. 21.1 us` at $C = 25$, `38.5 vs. 38.2 us` at $C = 50$, `73.5 vs. 74.9 us` at $C = 100$ on `scifact`).
   - Query `Encode p50 (us)` isolates the $O(n_q \cdot |V| \cdot d)$ linear adapter projection overhead (`154.2 to 154.8 us` for Arm 4 vs. `16.4 us` for Arm 3 on `scifact`; `37.5 to 37.9 us` vs. `6.2 us` on `nfcorpus`).
   - Stage-1 `Retrieve p50 (us)` (`SparsePostingIndex::top_k` with MaxScore pruning) is `2x` to `20x` slower under the synthetic SPLATE linear basis than under direct sparse activations (`115.8 vs. 58.2 us` on `scifact` at $C = 25$; `235.6 vs. 8.1 us` on `nfcorpus` at $C = 25$) because linear projection over compressed $d = 32$ token vectors produces flatter weight distributions with weaker MaxScore upper-bound pruning.
2. **Next Step to Close `#711`**:
   - Plug pinned trained model checkpoints (a trained SPLADE checkpoint for Arm 3, a trained ColBERT-style late-interaction checkpoint + trained SPLATE linear adapter checkpoint for Arm 4, and a trained cross-encoder bundle via `BundleCrossEncoder` for Arm 2) into `run_study_with_encoded` to measure trained-model retrieval quality and finalize the architectural decision for `#711`.
