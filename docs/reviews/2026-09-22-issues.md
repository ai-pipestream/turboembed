# Review of 2026-09-22: open defects

An independent review of the tree at `2b0db18` plus the untracked
`providers/metal/`. Scope: `crates/turbo-bench`, `providers/ggml`,
`providers/hailo`, `providers/metal`, `crates/turbo-core/src/handles.rs`,
`crates/turbo-capi`, `crates/turbo`, `bindings/java`, `bindings/swift`,
`demo/` (excluding `demo/java-web-spring`), `scripts/package.sh`,
`scripts/package-container.sh`, `packaging/Dockerfile`.

Nothing in this review was fixed. `cargo test --locked --workspace
--exclude turbo-provider-cuda`, `scripts/gen-header.sh --check` and
`scripts/gen-versioned.py --check` all pass on the reviewed tree, so every
item below is something the current suite does not catch.

`providers/metal/` was being edited while this review ran. Its line numbers
are against the file whose md5 is `d4bd23d820559681d9963db465408fed`
(`provider.mm`), `ab8a15cb3667e1d8264af7698e34867b` (`kernels.inc`) and
`792f8f20b0ebdfd5042e007b61983b4a` (`safetensors.hpp`). The kernels and the
forward pass were rewritten from per-row to whole-batch part way through
this review; findings 1 to 87 are against the batched version. Each finding quotes
the offending text so it can be relocated if the file moved on.

Findings are numbered most severe first.

## Memory safety and ABI soundness

1. **`describe_into` never bounds `ndim` by `TURBO_MAX_RANK`, so a caller
   controlled rank smashes the provider's stack.**
   `providers/hailo/src/provider.cpp:361` and `:366`,
   `providers/openvino/src/provider.cpp:328` and `:333`,
   `providers/metal/src/provider.mm:297` and `:301`, with the write at
   `providers/hailo/src/provider.cpp:322`,
   `providers/openvino/src/provider.cpp:284` and
   `providers/metal/src/provider.mm:258`.

   ```cpp
   for (uint32_t i = 0; i < in.ndim; ++i) {
   ```
   ```cpp
   b->desc = packed_desc(in.placement, in.dtype, std::vector<uint64_t>(in.shape, in.shape + in.ndim), elem);
   ```
   ```cpp
   d.shape[i] = shape[i];
   ```

   `turbo_types.h` documents `ndim` as 0 to 8 and `shape` is
   `uint64_t shape[TURBO_MAX_RANK]` with `TURBO_MAX_RANK` 8, but nothing in
   any of the three C or C++ providers checks it.

   Failure: call `buffer_alloc` through the vtable with
   `desc->struct_size = sizeof(turbo_buffer_desc)`, `dtype =
   TURBO_DTYPE_F32`, `bytes = 0`, `ndim = 200`, `shape[0] = 1`. The vector
   constructor reads 1600 bytes out of a 160 byte struct, and `packed_desc`
   then writes `d.shape[199]` at byte offset 1608 of a 160 byte stack local,
   about 1.4 KB of stack corruption inside the provider. The Rust core
   rejects `ndim > TURBO_MAX_RANK` in `BufferDesc::from_abi`
   (`crates/turbo-core/src/buffer.rs:92`), so this is reachable only through
   the direct vtable, which is a published ABI and is exactly how each
   provider's own `tests/provider_test.cpp` drives it.

   Fix: at the top of each `describe_into`, `require(in.ndim <=
   TURBO_MAX_RANK, TURBO_E_INVALID_SHAPE, ...)`. Better, move the guard into
   a shared helper in `native/provider_common/turbo_provider_common.hpp` so
   the next provider gets it for free.

2. **`buffer_export` writes up to 24 bytes past a caller's short
   `turbo_native_handle`.**
   `providers/hailo/src/provider.cpp:1174-1177`,
   `providers/openvino/src/provider.cpp:1276-1286`,
   `providers/metal/src/provider.mm:1104-1115`.

   ```cpp
   out->offset = 0;
   out->aux = 0;
   ```

   `turbo_versioned::size_is_known` accepts the truncated prefix layout
   `offsetof(turbo_native_handle, handle)` == 8
   (`native/provider_common/turbo_versioned.hpp:463`), so `check_size`
   passes for an 8 byte caller struct and the code then writes `kind`,
   `handle`, `aux` and `offset` unconditionally.

   Failure: a host built against an older ABI does
   `turbo_native_handle h{}; h.struct_size = 8;` on the stack and calls
   `buffer_export`. The provider returns `TURBO_OK` after overwriting 24
   bytes of the caller's stack frame, so the symptom is a corrupted adjacent
   local or a `__stack_chk_fail` abort far from the cause.

   Fix: build a local `turbo_native_handle full{}`, set
   `full.struct_size = out->struct_size`, and
   `std::memcpy(out, &full, out->struct_size)`. This is the `write_sized`
   pattern the same files already use for `turbo_device_info` and
   `turbo_capability`.

3. **The gRPC demo server reinterprets a result as `float` without checking
   its dtype, giving a heap out of bounds read served as a successful RPC.**
   `demo/grpc-c-server/src/server.cpp:138` and `:146`.

   ```cpp
   std::vector<float> buf(ri.bytes / sizeof(float));
   ```
   ```cpp
   emb->mutable_values()->Add(buf.begin() + r * ri.dim, buf.begin() + (r + 1) * ri.dim);
   ```

   Failure: run the server against a bundle whose output dtype is f16 (the
   reason `turbo_embed_options.output_dtype` exists). Then
   `ri.bytes = batch * dim * 2`, so `buf.size() == batch * dim / 2`, while
   the loop walks to `buf.begin() + batch * dim`. For `batch = 4, dim = 384`
   it reads 3072 floats out of a 768 float vector and returns the garbage to
   the client with `grpc::Status::OK`. `demo/c/main.c:134` and
   `demo/python/turbo_demo.py:149` both check the dtype; the server is the
   only consumer that does not.

   Fix: reject any dtype other than `TURBO_DTYPE_F32` with
   `grpc::Status(INVALID_ARGUMENT, ...)`, and assert
   `buf.size() >= size_t(ri.batch) * ri.dim` before the copy loop.

4. **`session_write_tokens` accepts `row_stride < seq` and reads past the
   caller's array.**
   `providers/hailo/src/provider.cpp:1286` and `:1300`,
   `providers/openvino/src/provider.cpp:1379`,
   `providers/metal/src/provider.mm:1226` and `:1230`.

   ```cpp
   const uint32_t stride = batch->row_stride == 0 ? batch->seq : batch->row_stride;
   ```

   `turbo_token_batch` documents `row_stride` as "Elements between row
   starts; 0 = `seq`", so a stride smaller than `seq` is inconsistent, and
   the last row reads `(batch - 1) * stride + seq` elements.

   Failure: pass `batch = 8`, `seq = 128`, `row_stride = 64` over an array
   sized `8 * 64 == 512` int32s. The final `memcpy` reads
   `batch->ids[448..575]`, 256 bytes past the end of a 2 KB allocation. The
   Rust core's `TokenBatch::validate`
   (`crates/turbo-core/src/provider.rs:357`) sizes its own check from
   `required_len`, so again this is the direct vtable path.

   Fix: `require(batch->row_stride == 0 || batch->row_stride >= batch->seq,
   TURBO_E_INVALID_SHAPE, "row_stride must be 0 or at least seq")` before
   the loop, in all three providers.

5. **The Python demo sets no `argtypes`, so `turbo_result_read`'s 64 bit
   `capacity` is passed as a 32 bit int.**
   `demo/python/turbo_demo.py:153`.

   ```python
   t.check(lib.turbo_result_read(result, 0, buf, ri.bytes, C.byref(written), C.byref(err)), "turbo_result_read")
   ```

   The signature is `turbo_result_read(turbo_result *, uint32_t, void *,
   uint64_t capacity, uint64_t *written, turbo_error *)`. With no
   `argtypes`, ctypes passes a Python int as `ffi_type_sint`. Only two
   `restype` assignments exist in the file (lines 75 and 76) and no
   `argtypes` at all.

   Failure: a 4 GiB + 1 KiB result (batch 1.4M by dim 768 f32) makes
   `capacity` arrive as 1024 while `buf` really holds 4 GiB, so the call
   fails with `TURBO_E_CAPACITY` claiming the caller's buffer is 1 KiB. The
   upper 32 bits are unspecified for smaller values, so today's success on
   x86-64 is an ABI accident; on an ABI where a 64 bit argument occupies an
   aligned register pair (32 bit ARM) every later argument shifts and
   `written` and `err` become wild pointers. This demo is consumer facing
   documentation for the C ABI, so it teaches the bug.

   Fix: set `restype` and `argtypes` for every function the demo calls.

6. **Input descriptors are read in full regardless of the caller's declared
   `struct_size`.**
   `providers/hailo/src/provider.cpp:1124-1125`, `:1222-1223`, `:1136-1138`,
   `:1150-1152`, `:1282-1300`, `:1336`, and the same pattern in
   `providers/metal/src/provider.mm:1055-1057`, `:1162-1164`, `:1069` and
   `:1081`, and `providers/openvino/src/provider.cpp`.

   ```cpp
   require(desc->next == nullptr, TURBO_E_INVALID_ARGUMENT, "turbo_session_desc.next must be NULL");
   reject_unknown(options_of(desc->options, desc->n_options, "session"), {}, "hailo session");
   ```

   AGENTS.md's ABI rules say "The library reads only fields below the
   caller's declared size." `check_size` accepts a shorter prefix (for
   example `turbo_session_desc` accepts 8, per
   `native/provider_common/turbo_versioned.hpp:225`) and the code then reads
   every field.

   Failure: a host declares `turbo_session_desc d{}; d.struct_size = 8;
   d.max_batch = 4;` on the stack. `x_session_create` reads `max_seq` at
   offset 8, `n_options` at 12, `options` at 16 and `next` at 24, all past
   the end of an 8 byte object; if the adjacent stack slot is non zero,
   `options_of` dereferences a garbage `turbo_kv *` and segfaults inside the
   provider. `x_buffer_alloc` is worse: `b->desc = in` copies the whole 160
   byte `turbo_buffer_desc`.

   Fix: add a `read_prefix<T>` helper to
   `native/provider_common/turbo_provider_common.hpp` that zero initializes
   a local, runs `check_size<T>`, then
   `memcpy(&local, p, min(p->struct_size, sizeof(T)))`, and route every
   descriptor read through it. `x_session_write_text` already does this by
   hand (`providers/hailo/src/provider.cpp:1247`,
   `providers/metal/src/provider.mm:1186`), so the intended pattern exists.

7. **Ten `turbo-capi` entry points form `&mut *out` on a caller pointer,
   asserting alignment and initialization the C ABI does not promise.**
   `crates/turbo-capi/src/lib.rs:401`, and identically at `:493`, `:673`,
   `:806`, `:864`, `:1146`, `:1187`, `:1223`, `:1481`, `:1647`.

   ```rust
   let o = unsafe { &mut *out };
   ```

   Each reads only `o.struct_size`, but forming
   `&mut turbo_device_info` requires an aligned, fully initialized value.
   `turbo_device_info`, `turbo_buffer_desc`, `turbo_session_stats` and
   `turbo_result_info` all contain `uint64_t`, so alignment is 8, while the
   idiomatic C usage leaves every field but `struct_size` uninitialized.

   Failure: a JNI or FFM binding carves an out parameter from a byte buffer
   at a 4 byte offset (`MemorySegment.asSlice(4)`), or a C++ host uses a
   `#pragma pack` struct. `&mut *out` is immediate UB; it happens to work on
   x86 today and can fault on aarch64 or under a future vectorized copy.

   Fix: use the pattern already present one function away at
   `crates/turbo-capi/src/lib.rs:738`:
   `let size = unsafe { out.cast::<u32>().read_unaligned() };` then
   `check_size::<T>(..., size)?`.

8. **A generation chunk with no text hands the caller a dangling `0x1`
   pointer while its two neighbouring array fields are explicitly NULL.**
   `crates/turbo-capi/src/lib.rs:1490` and the identical line at `:1570`.

   ```rust
   text: turbo_text { ptr: chunk.text.as_ptr().cast(), len: chunk.text.len() as u64 },
   ```

   `tokens` and `logprobs` on the lines above and below are nulled when
   empty, but `String::as_ptr()` on an unallocated `String` returns
   `align_of::<u8>()`, that is `0x1`.

   Failure: a binding that branches on `chunk.text.ptr != NULL` rather than
   on `len`, which the inconsistency with the two neighbouring fields
   invites, dereferences `0x1` and segfaults.
   `crates/turbo-conformance/tests/generation_c.rs:555` explicitly notes
   that "a binding can branch on the pointer as well as on the count", which
   is the behavior this line makes unsafe.

   Fix: emit `turbo_text { ptr: std::ptr::null(), len: 0 }` when
   `chunk.text.is_empty()`, at both sites.

9. **`turbo_error.struct_size` is never validated against its `Versioned`
   table, and a size in 8..12 leaves `field` stale from a previous call.**
   `crates/turbo-capi/src/lib.rs:93-97`.

   ```rust
   let size = unsafe { (*err).struct_size };
   if size < 8 {
   ```

   `turbo_error`'s accepted sizes are `[8, 12, 508]`
   (`crates/turbo-abi/src/versioned.rs:31-36`) but `boundary` only rejects
   `< 8`; `check_size::<turbo_error>` is never called, unlike every other
   descriptor in the file.

   Failure: a caller sets `err.struct_size = 9`. `clear` (lines 74-85) and
   `fail` (lines 43-68) both write `code` but skip `field` because
   `size >= 12` is false. A call that previously failed with
   `TURBO_E_UNSUPPORTED_OPTION, field = 6` is followed by one that fails
   with `TURBO_E_INVALID_ARGUMENT`; the caller reads the new code next to a
   stale `field = 6` and blames the wrong option, with no
   `TURBO_E_INVALID_STRUCT_SIZE` to warn it.
   `crates/turbo-conformance/tests/contract_c_errors.rs:229-243` only
   exercises 4 and 8.

   Fix: replace the `size < 8` test with
   `check_size::<turbo_error>("turbo_error", size)`, keeping the special
   case that a size below 8 cannot be written at all, and add conformance
   cases for 9 and 507.

## Wrong results and lost work

10. **The ggml stop string is matched only as a suffix of the holdback, so a
    stop inside a token is missed and a repeated stop is emitted.**
    `providers/ggml/src/lib.rs:910`.

    ```rust
    if let Some(s) = self.plan.stop.iter().find(|s| !s.is_empty() && self.hold.ends_with(s.as_str())) {
    ```

    Failure A, missed entirely: `stop = ["```"]` and the model emits the
    single token `` "```\n" `` (one token in most code tuned BPE
    vocabularies). `hold` ends with `"\n"`, so `ends_with("```")` is false,
    no stop fires, `release_held` emits it, and generation runs to
    `max_new_tokens`. The caller gets the stop string plus everything after
    it and `finish_reason` is `Length` instead of `Stop`.

    Failure B, the stop string itself is emitted: `stop = ["\n"]` and the
    model emits the token `"\n\n"`. `hold = "\n\n"`, `ends_with("\n")` is
    true, `keep = 2 - 1 = 1`, so `out.text` receives `"\n"`, which is
    exactly what the holdback exists to prevent. The comment on lines
    911-913 claiming "the whole match is withheld" is wrong whenever the
    stop occurs more than once or is not flush with the end.

    Fix: find the earliest start offset over all stop strings,
    `self.plan.stop.iter().filter(|s| !s.is_empty()).filter_map(|s|
    hold.find(s.as_str()).map(|i| (i, s.len()))).min()`, emit
    `hold[..i]`, and finish. Start the search at
    `hold.len() - piece.len() - hold_max` so a stop already released in an
    earlier step is not re-detected.

11. **`piece()` aborts the whole ggml generation on any non-EOG control
    token and on any piece longer than 16 bytes.**
    `providers/ggml/src/lib.rs:755`.

    ```rust
    .token_to_piece_bytes(token, 16, false, None)
    .map_err(|e| Error::internal(format!("token {} has no piece: {e}", token.0)))?;
    ```

    `llama_vocab::impl::token_to_piece` returns 0 when
    `!special && (attr & (UNKNOWN|CONTROL))`, which the Rust wrapper maps to
    `Err(TokenToStringError::UnknownTokenType)`; line 900 returns early only
    for EOG tokens. Separately, `_try_copy` returns a negative size when the
    16 byte buffer is too small, and unlike the crate's own
    `token_to_bytes` this code does not retry with the reported size.

    Failure: Qwen2.5-0.5B-Instruct with plain `max_new_tokens: 64` emits
    `<|im_start|>` (id 151644, attribute CONTROL, not in the EOG set) trying
    to open another turn. `step` returns `TURBO_E_INTERNAL` "token 151644
    has no piece: Unknown Token Type", every token generated so far is lost
    and the generation handle is unusable. The same happens on the first
    token longer than 16 bytes, which is ordinary for identifiers such as
    `ArgumentNullException` or any six character CJK run.

    Fix: retry with the size the error reports
    (`Err(InsufficientBufferSpace(i)) => retry with (-i) as usize`), and
    decide control tokens explicitly by checking `model.token_attr(token)`
    rather than letting the error path swallow them.

12. **A single undecodable byte wedges the ggml `pending` buffer and
    permanently loses all remaining text.**
    `providers/ggml/src/lib.rs:758`.

    ```rust
    let valid = match std::str::from_utf8(&self.pending) {
        Ok(_) => self.pending.len(),
        Err(e) => e.valid_up_to(),
    };
    ```

    `error_len()` is never consulted, so a genuinely invalid byte is
    indistinguishable from an incomplete tail. Once one is in `pending`,
    `valid_up_to()` returns the same index forever: `text` is always empty,
    `pending` grows without bound, and `hold` never receives another byte.
    `finish()` (line 726) flushes `hold` but never `pending`.

    Failure: a byte fallback SPM vocabulary under a tight `logit_bias` emits
    a lone `<0xE6>` byte token not followed by valid continuation bytes.
    From that step on every chunk has a token id and empty text; the caller
    receives 500 token ids and no text at all, with
    `finish_reason = Length` and no error.

    Fix: branch on `e.error_len()`. `None` means an incomplete tail, keep
    buffering; `Some(n)` means invalid bytes, emit `U+FFFD` and
    `drain(..valid + n)`. Also flush any remaining `pending` in `finish()`.

13. **`bench_generate` starts its clock after the prefill, so both
    `time_to_first_token_ms_p50` and `total_ms_p50` in every committed
    generate receipt exclude the entire prompt pass.**
    `crates/turbo-bench/src/main.rs:687-688`.

    ```rust
    g.prompt(&messages).map_err(|e| format!("prompt: {e}"))?;
    let t0 = Instant::now();
    ```

    `Generation::prompt` is not a staging call:
    `crates/turbo-core/src/handles.rs:876` calls `st.inner.prompt(messages)`
    and the ggml implementation ends with `self.prefill()`
    (`providers/ggml/src/lib.rs:832`), so the whole prompt decode runs
    inside `prompt()`.

    Failure: `testdata/receipts/turbo/bench/ggml-krick-cpu-generate-2026-09-21.json`
    reports `time_to_first_token_ms_p50: 11.92` with `prompt_tokens: 19` and
    `decode_tokens_per_s_p50: 81.1` (12.3 ms per token), so the published
    TTFT is exactly one decode step and the 19 token prefill is invisible.
    A provider that regressed its prefill tenfold would show no change in
    any published number and `--budget` on `generate total` would pass.

    Fix: take `t0` before `prompt()` so TTFT spans prompt submission to
    first token, and keep the decode rate as (tokens after the first) over
    (total minus ttft). If setup must be excluded, time `prompt()`
    separately and publish an explicit `prefill_ms_p50` rather than dropping
    it.

14. **The ggml embedding context divides its KV budget by `max_batch`, so
    rows well inside `max_seq` fail to decode on decoder style embedders.**
    `providers/ggml/src/lib.rs:988-993`.

    ```rust
    let ubatch = n_tokens.min(EMBED_UBATCH_CAP).max(max_seq);
    let params = LlamaContextParams::default()
        .with_n_ctx(NonZeroU32::new(ubatch))
        .with_n_batch(ubatch)
        .with_n_ubatch(ubatch)
        .with_n_seq_max(max_batch)
    ```

    `n_ctx` is set to the micro batch size while `n_seq_max` is the whole
    batch. `kv_unified` defaults to false, and with it false
    `cparams.n_ctx_seq = cparams.n_ctx / cparams.n_seq_max` padded to 256,
    and that is what sizes each sequence's KV stream.

    Failure: an embedding bundle over a decoder backbone
    (`contract.pooling = "last"`, which this provider supports at line 976),
    `max_seq = 512`, `limits.max_batch` unset so `max_batch = 32`. Then
    `n_tokens = 16384`, `ubatch = 4096`, `n_ctx_seq = 4096 / 32 = 128`.
    `write_text` accepts a 400 token row and `run` fails with
    `TURBO_E_RUNTIME` "llama.cpp decode failed" for an input the session
    advertised as legal. BERT family encoders are unaffected because
    llama.cpp creates no KV cache for them, which is presumably why this was
    not caught.

    Fix: pass `kv_unified = true` on the embedding context, or set `n_ctx`
    to `ubatch * max_batch` while keeping `n_batch` and `n_ubatch` at
    `ubatch`. Either way assert `llama_n_ctx_seq(ctx) >= max_seq` after
    creation and fail loudly rather than at first decode.

15. **`ggml` `Truncate::Left` silently deletes the `prompt_role` prefix.**
    `providers/ggml/src/lib.rs:1090`.

    ```rust
    Truncate::Left => &content[content.len() - keep..],
    ```

    The prefix is prepended before tokenization (line 1062,
    `format!("{prefix}{text}")`) and sits at the front of `content`, exactly
    where left truncation cuts.

    Failure: an e5 or bge bundle with `prefix_query = "query: "`,
    `prompt_role = QUERY`, `truncate = LEFT`, and an input longer than
    `max_seq`. The prefix is dropped, so the vector lands in the document
    subspace instead of the query subspace and retrieval quality collapses,
    with `TURBO_CAP_OPT_PROMPT_ROLE` reported set and no error. The core
    explicitly refuses a role the bundle has no prefix for
    (`crates/turbo-core/src/handles.rs:398-406`) on exactly this reasoning.

    Fix: tokenize prefix and text separately, keep the prefix tokens whole,
    and left truncate only the text tokens; or reject the combination naming
    field 2.

16. **A caller named stop token's own text is emitted, unlike EOS.**
    `providers/ggml/src/lib.rs:906`.

    ```rust
    if self.plan.stop_tokens.contains(&token.0) {
        self.finish(out, FinishReason::Stop);
    ```

    `piece()` runs at line 905 and its output is pushed into `hold` before
    this check, and `finish()` flushes `hold` into `out.text`. The EOS path
    at line 900 returns before `piece()`, so EOS text is withheld. The two
    stop mechanisms behave oppositely.

    Failure: `stop_tokens = [id of "\n\nUser"]`. Generation stops correctly
    but `out.text` ends with `"\n\nUser"`, so a caller concatenating chunks
    into a conversation turn gets the delimiter glued onto the assistant
    message. The same stop expressed as a string would have been withheld.

    Fix: move the `stop_tokens.contains` check above line 905, keeping the
    id in `out.tokens`.

17. **The Metal embedding kernel substitutes a zero row for an out of range
    token id instead of failing, and nothing upstream closes the gap.**
    `providers/metal/src/kernels.inc:76-80`, reachable through
    `providers/metal/src/provider.mm:1228-1242`.

    ```metal
    } else {
        for (uint h = 0; h < p.hidden; ++h) {
            row[h] = 0.0f;
        }
    }
    ```

    `x_session_write_tokens` never validates ids against `m->word_rows`, and
    the core's `TokenBatch::validate`
    (`crates/turbo-core/src/provider.rs:375`) only range checks ids when
    `vocab_size != 0`. `Bundle` defaults `vocab_size` to 0 when the manifest
    omits it (`native/provider_common/turbo_provider_common.hpp:229`), and
    every shipped fixture under `testdata/bundles/mock/` omits it, so the
    default path is the unchecked one. The load time check at
    `providers/metal/src/provider.mm:474` is `b.vocab_size == 0 ||
    word.rows() == b.vocab_size`, so it never compares the tokenizer's vocab

    Failure: a bundle without `contract.vocab_size` whose `tokenizer.json`
    has more entries than the checkpoint's word embedding table. Every token

    `TURBO_OK`, and the caller gets quietly wrong vectors with no error
    anywhere. This is the "silently substitutes a value" case PLAN.md

    Fix: validate every id and token type against `word_rows` and
    `type_rows` in `x_session_write_tokens` with
    `TURBO_E_INVALID_ARGUMENT`, and make the kernel's out of range branch
    unreachable. Separately, require that the loaded WordPiece vocabulary
    size equals `word.rows()` at load time.

18. **The Metal provider silently clamps the bundle's `contract.max_seq`
    down to the checkpoint's position count, where the other providers
    reject the mismatch.**
    `providers/metal/src/provider.mm:461`.

    ```cpp
    m->max_seq = b.max_seq == 0 ? max_position : std::min(b.max_seq, max_position);
    ```

## Leaks and resource lifetime

20. **Swift `Model.init` leaks the C model handle on any throw after it
    acquires one.**
    `bindings/swift/Sources/PipestreamTurbo/PipestreamTurbo.swift:311` and
    `:315`.

    ```swift
    rawHandle = out!
    ```
    ```swift
    try check { turbo_model_get_info(out!, &mi, $0) }
    ```

    At line 315, and again at 319 (`turbo_model_label`) and 322
    (`decodeEnum(mi.task)`), the instance is not fully initialized because
    the stored property `info` is still unassigned. Swift emits
    `dealloc_partial_ref` for a throw before full initialization, so
    `deinit { close() }` does not run and `turbo_model_release` is never
    called.

    Failure: load a bundle whose `task` is a constant this binding predates.
    `turbo_model_load` succeeds, `decodeEnum(mi.task, "task")` throws
    `TURBO_E_INVALID_ENUM`, the caller catches it and retries with another
    bundle. Each attempt permanently leaks one loaded model, its weights and
    provider allocations, plus the retained context and runtime, which can
    now never be released. In a server loop this is unbounded.

    Fix: acquire the handle into a local and release it before rethrowing
    (`do { ... } catch { turbo_model_release(out!); throw error }`), or
    initialize `info` to a placeholder so the instance is fully initialized
    before the fallible work.

## Benchmark and receipt integrity

44. **The receipt's `commit` is silently `"unknown"`, or silently the HEAD
    of whatever unrelated repository the tool was run in.**
    `crates/turbo-bench/src/main.rs:276` and `:756`.

    ```rust
    .unwrap_or_else(|| "unknown".to_string())
    ```
    ```rust

    ```

    `run_cmd` discards the spawn error, discards a non zero exit, and
    substitutes `"unknown"`. `git rev-parse HEAD` runs in the process's cwd,
    not the repository the binary was built from, and nothing records
    whether the tree was dirty.

    Failure: running the binary from a non git directory produced a receipt
    with `"commit": "unknown"` and exit 0 (reproduced). Running it from any
    other checkout stamps that checkout's HEAD onto a TurboEmbed benchmark
    receipt. `machine.hostname` and `machine.os` degrade the same way.
    PLAN.md section 7 makes a measurement without a commit worthless.

    Fix: resolve the commit at build time from a `build.rs` captured
    `git rev-parse HEAD` plus a dirty flag, or run
    `git -C <repo root> rev-parse HEAD` and fail the run with a named error
    when it does not resolve. Never write `"unknown"` into a receipt field.

    a comment or a doc string instead of the type."

    Failure: a direct vtable host (the pattern each provider's
    `tests/provider_test.cpp` uses) calls `model_release(m)` while a session
    created from `m` is still live, then calls `session_run` on it. The
    session dereferences the freed `Model`, typically crashing inside
    `std::mutex::lock`. Ranked low because

    ordering holds for every caller going through the core, and all three
    providers share the pattern.

    Fix, if the house decides a provider must be self defending: make
    `Model` and `Context` `shared_ptr` managed with `Session` holding a

87. **`Enc::dispatch_groups` hardcodes a 256 thread threadgroup without
    checking the pipeline's own limit.**
    `providers/metal/src/provider.mm:735-742`, used at `:805`.


    The sibling `dispatch` helper clamps to
    `pso.maxTotalThreadsPerThreadgroup` (line 729); `dispatch_groups` does
    not, and the tiled `linear_nt_kernel` requires all 16 by 16 threads to

    observed failure, but it is unchecked and the check is one line.

    Fix: `require(pso.maxTotalThreadsPerThreadgroup >= tg_x * tg_y,
    TURBO_E_DEVICE_UNAVAILABLE, ...)` naming the kernel and both numbers,
    or pick the tile size from the pipeline's reported limit at load time.
