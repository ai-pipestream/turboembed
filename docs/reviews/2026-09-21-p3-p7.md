## HIGH

### H-1. CUDA token classification emits a zero-token word span that steals the next word's label and byte range. CONFIRMED (reproduced).

`providers/cuda/src/wordpiece.rs:331-389`, specifically the missing guard between `:377` and `:383`.

The OpenVINO C++ this was ported from has the guard explicitly:

```cpp
// providers/openvino/src/provider.cpp:902-904
if (nw == 0) {
    continue; // the normalizer dropped it; it occupies no column
}
```

The Rust port dropped it. Its three branches are `seen + nw <= skip` (before the window), `seen < skip` (cut on the left), `seen + nw > skip + take` (cut on the right). A word with `nw == 0` falls through all three and is pushed with `n_tokens: 0` and `first_token: tok`, which is the column the *next* word occupies.

Reachable with ordinary text. Probed against the committed MiniLM tokenizer through the real `native/wordpiece` encoder (`wordpiece_tokenize` returns `ntok=0`) for: a lone combining mark U+0301, soft hyphen U+00AD, zero-width space U+200B, ZWJ U+200D, variation selector U+FE0F, and U+FFFD. `native/wordpiece/encode.cpp:222` drops `cp == 0 || cp == 0xFFFD || is_control(cp)` and `:235` drops nonspacing marks under `strip_accents`.

Reproduced end to end by calling the shipped `encode_row` (scratch crate that `#[path]`-includes `providers/cuda/src/wordpiece.rs` and links `native/wordpiece`):

```
text="New \u{200d} York is here" live_tokens=6 ids=[101, 2047, 2259, 2003, 2182, 102]
   span bytes[0,3)  = "New"        first_token=1 n_tokens=1
   span bytes[4,7)  = "\u{200d}"   first_token=2 n_tokens=0   <-- bogus
   span bytes[8,12) = "York"       first_token=2 n_tokens=1
```
Same for U+00AD and U+FE0F.

Failure: `aggregate_spans` (`providers/cuda/src/lib.rs:1263-1275`) passes the bound check (`2 + 0 > seq` is false), reads `token_label` at column 2 — which is `york` — and labels the invisible run with York's tag. With `B-LOC` it emits an extra entity span over bytes 4..7; with `I-LOC` it opens the group there and the merged span becomes `[4,12)` instead of `[8,12)`. Silently wrong NER output, returned as `TURBO_OK`.

Violates principle 1: the header is one contract and the two providers must produce the same spans for the same bytes; they do not. It is also the H4 class the OpenVINO side just fixed, reintroduced in the port.

The test that should catch it cannot. `providers/cuda/tests/wordpiece.rs:26` has exactly the right shape (it checks each span's claimed columns hold that word's own ids) but (a) its `TEXT` at `:17` is pure Latin, and (b) its ordering assertion at `:71` is `pair[0].first_token + pair[0].n_tokens <= pair[1].first_token`, which `2 + 0 <= 2` satisfies. Fixing this needs the guard, a non-Latin input, and `assert!(w.n_tokens > 0)`.

### H-2. The ggml embedding session sizes `n_batch` and `n_ubatch` at `max_batch * max_seq`, so its compute buffer grows quadratically with the session shape. CONFIRMED (measured).

`providers/ggml/src/lib.rs:915-921`:
```rust
let n_tokens = max_batch.checked_mul(max_seq)...;
let params = LlamaContextParams::default()
    .with_n_ctx(NonZeroU32::new(n_tokens))
    .with_n_batch(n_tokens)
    .with_n_ubatch(n_tokens)
```

A non-causal encoder needs each *sequence* inside one micro-batch, i.e. `n_ubatch >= max_seq`; llama.cpp packs several sequences per ubatch itself. Sizing the ubatch at the whole batch forces llama.cpp to reserve the worst-case graph for `batch*seq` tokens, whose attention mask alone is `n_ubatch^2` floats.

Measured through the public C ABI against `~/opt/bundles/minilm-gguf` on the ggml CUDA device, RSS delta for `turbo_session_create` alone (no run):

| max_batch x max_seq | n_tokens | RSS delta |
|---|---|---|
| 1 x 128 | 128 | 2.8 MB |
| 8 x 256 | 2 048 | 28.5 MB |
| 16 x 256 | 4 096 | 86.7 MB |
| 32 x 256 | 8 192 | 305.3 MB |

Doubling the tokens costs 3.0x then 3.5x — superlinear, as predicted. For a 23 MB model. Extrapolating, the session shape the ggml README implies for a 512-token bundle at batch 32 costs over a gigabyte, and on a GPU it is VRAM. The live tests never see it because they use 8x256 and 16x128.

Not a memory-safety bug, but it is a resource contract the ABI does not let a caller discover, and `turbo_session_create` will OOM on shapes the model info says are legal (`max_batch` is 32 by default from `load_model`). Fix: `with_n_ubatch(max_seq)` and `with_n_batch(n_tokens)`.

### H-3. A ggml stop string that spans token boundaries leaks its prefix into the stream. CONFIRMED (traced).

`providers/ggml/src/lib.rs:851-856`:
```rust
if let Some(s) = self.plan.stop.iter().find(|s| !s.is_empty() && self.text_acc.ends_with(s.as_str())) {
    let keep = out.text.len().saturating_sub(s.len());
    out.text.truncate(keep);
```

Detection is right: `text_acc` accumulates every piece, so a stop string spanning tokens is found. The retraction is not: `out.text` holds only *this* step's piece, and the earlier bytes of the stop string were already delivered to the caller in earlier chunks and cannot be taken back.

`stop = "</s>"` tokenized as `<`, `/`, `s`, `>`: steps 1-3 hand the caller `<`, `/`, `s`; step 4's `saturating_sub` gives `keep = 0` and drops `>`. The caller's concatenated stream ends `...</s`. The doc comment on the line above says "Hand back the text before the stop string only."

`TURBO_CAP_OPT_GEN_STOP_STRINGS` is set in `GGML_CAPS` (`lib.rs:81`), so principle 2 requires it honored exactly. The correct shape is to hold back `max(stop.len()) - 1` bytes of decoded text before emitting. (No panic risk: I checked every path into `truncate`, and `keep` is always a char boundary.)

## MEDIUM

### M-1. CUDA `Truncate::LEFT` refuses inputs it advertises it can truncate. CONFIRMED (traced).

`providers/cuda/src/wordpiece.rs:231` sizes `RowScratch` at `seq * 16` ids; `:298-303` refuses with `TURBO_E_CAPACITY` when `n_text > scratch.ids.len()`. `TURBO_CAP_OPT_TRUNCATE` is in `CUDA_CAPS` (`providers/cuda/src/lib.rs:79`).

With a 128-column session the ceiling is 2 048 tokens, roughly 8 KB of prose; with 512 columns, 8 192 tokens. Left-truncating a long document — the case left truncation exists for — fails with a resource error. Loud, not silent, so it does not violate the letter of principle 2, but it is an advertised option that does not work on the inputs it is for. `Truncate::RIGHT` has no such ceiling (it tokenizes straight into the row), so the two directions have different domains.

### M-2. Two turbo sessions on one CUDA model serialize on the model mutex. CONFIRMED (traced).

`providers/cuda/src/lib.rs:1108` takes `model.session.lock()` around `run_binding` for the whole graph execution. PLAN.md 4.2 states "Distinct sessions on one model run concurrently", and `TURBO_CAP_WEIGHT_SHARING` is advertised.

The lock is forced by the crate: `ort::Session::run_binding(&'s mut self, ...)` (`ort-2.0.0-rc.13/src/session/mod.rs:374`) takes `&mut Session` even though the inner `run_binding_inner` takes `&self`. The honest options are either to stop advertising concurrent sessions for this provider or to use one `ort::Session` per turbo session (giving up weight sharing) — the current state advertises both and delivers neither.

### M-3. `host_allocs: 0` is a false counter, and the conformance allocation test cannot catch it. CONFIRMED (traced).

`providers/cuda/src/lib.rs:1478` and `providers/ggml/src/lib.rs:1110` both report `host_allocs: 0`. CUDA's `run()` allocates on the host every call: `Vec<Output>` (`lib.rs:1428`), the shape `Vec<u64>` (`:1418-1426`), `tensor.shape().to_vec()` and the `expect` vec in `execute()` (`:1114-1118`), and `self.spans.clone()` (`:1452`). The core adds `Vec::with_capacity` per output in `plugin.rs:761`.

The suite asserts only that the counter does not *grow*: `crates/turbo-conformance/tests/allocation_rust.rs:31` and `allocation_c.rs:31` compare `end.host_allocs == warm.host_allocs`. A hardcoded 0 passes trivially, so the allocation check is vacuous for both new providers. PLAN.md 4.5 says the suite "asserts `allocs_per_run == 0` on the provider's own counter"; today it asserts nothing. Principle 7.

### M-4. ggml `write_tokens` silently reindexes a row with interior masking, and ignores `token_type_ids`. CONFIRMED (traced).

`providers/ggml/src/lib.rs:1036`:
```rust
row.extend(ids.iter().zip(mask).filter(|(_, m)| **m != 0).map(|(&id, _)| LlamaToken(id)));
```
Masked positions are dropped wherever they are, so a caller who masks token 5 of 20 gets a 19-token sequence with every later position shifted by one, not an error. `batch.types` is never read. The comment calls masked positions "padding", which is true only for trailing masks.

Principle 2: the mask is a caller-set input and it is being reinterpreted, not honored or refused.

### M-5. ggml `logprobs` returns bare floats from the raw logits, not from the sampling distribution, and rebuilds the whole vocabulary every step. CONFIRMED (traced).

`providers/ggml/src/lib.rs:741-750`. It log-softmaxes the full logits vector, sorts it descending, and hands back the first `k` values with no token ids. So the caller cannot tell which token each number belongs to, and the numbers do not reflect the sampler chain the token was actually drawn from (`logit_bias`, the grammar, the EOG suppression for `min_new_tokens`, `top_k`/`top_p`/`min_p`/`temperature`) — with a grammar in play they can be the logprobs of tokens the grammar forbade. `TURBO_CAP_OPT_GEN_LOGPROBS` is advertised (`lib.rs:79`). The full-vocab `Vec<f32>` allocation and sort per step is also on the hot path.

Either the header should state that `logprobs` is the pre-sampling distribution, or the values should come from the sampler's `LlamaTokenDataArray`.

### M-6. ggml embedding truncation assumes a special token at both ends. PLAUSIBLE (traced).

`providers/ggml/src/lib.rs:996-1010` splits `tokens` into `(tokens[0], tokens[len-1])` and cuts the middle. That is right for a BERT GGUF (`add_special` gives `[CLS] ... [SEP]`) and wrong for a decoder-style embedder where `AddBos` adds BOS only: `tokens[len-1]` is content, and under `Truncate::Right` the row becomes `BOS content[..keep] <the original final content token>` — a sequence the model never saw in training, and for `Pooling::Last` the pooled vector is read from exactly that spliced token. `GGML_CAPS` advertises `OPT_TRUNCATE` for every bundle the provider accepts, and `can_run` accepts any `Embedding` GGUF. Marked PLAUSIBLE because I did not have a decoder-style GGUF embedder to run.

## LOW

**L-1 (CUDA, PLAUSIBLE).** The post-processing kernels' correctness rests on an undocumented ONNX Runtime behavior. `providers/cuda/src/lib.rs:1129` says "The EP synchronized its stream when `run` returned"; `ort`'s `run_binding_inner` (`src/session/mod.rs:388-415`) calls `RunWithBinding` and never `SynchronizeBoundOutputs`, so this depends on the CUDA EP's default `OnRunEnd` sync. It is true today, but `ort` exposes `IoBinding::synchronize_outputs()` (`src/session/io_binding.rs:212`) and it is not used. Setting a user compute stream or `kOrtRunOptionsConfigDisableSynchronizeExecutionProviders` would make the kernels read the output before the graph finished, silently and nondeterministically.

**L-2 (CUDA).** `turbo_result_buffer` on an embedding result hands back a device buffer whose descriptor says `[max_batch, dim]` and `bytes = max_batch*dim*4`, while the content is `[n_rows, output_dim]` packed at the front (`providers/cuda/src/lib.rs:1148`, `:1418-1426`). `turbo_result_output_info` carries the truth; the buffer descriptor a `DEVICE_RESULT` consumer would naturally read does not.

**L-3 (core).** The field-boundary `struct_size` rule is sound only because every count/pointer consumer NULL-checks (`abi_convert.rs:113-123, 129-147, 563-579`; `capi/src/lib.rs:1006-1013`; `plugin.rs:742, 782, 873, 881`). It is not sound by construction: `versioned.rs`'s own doc comment claims "every accepted prefix is a layout that could have shipped", which is false for `turbo_generate_desc` (no version ever had `n_stop` without `stop`) and for `turbo_runtime_desc`, `turbo_token_batch` and every other count-before-pointer struct. The rule is really "every accepted prefix is safe *because* a truncated pointer reads NULL and every consumer refuses NULL with a non-zero count". That is a fine rule, but it should be stated as the invariant, since M-7 shows the laxer C++ copy already relies on the weaker claim.

**L-4 (core).** `turbo_buffer_export` was fixed to read only the leading `u32` with `read_unaligned` (`capi/src/lib.rs:737-739`), but `x_session_run`, `x_session_stats`, `turbo_result_info` (`capi/src/lib.rs:1187`) and their siblings still form `&mut *out` over a struct the caller may have declared shorter. Same technical UB, fixed in one place and not the rest. This was already "Low, open" in the first review; noting only that the new fix made the tree inconsistent.

**L-5 (capi `turbo_generate`).** When `n_tokens == 0` the chunk carries a dangling non-null `tokens` pointer (`capi/src/lib.rs:1560`) while `logprobs` is explicitly NULL when empty (`:1563`). A C callback that checks for NULL on one and not the other is being told two different things by the same struct.

**L-6 (ggml).** An unseeded generation uses a fixed `0xDEAD_BEEF` (`providers/ggml/src/lib.rs:538`), so two calls with `temperature > 0` and no seed produce identical text. Defensible as reproducibility, but it is not what a caller who omitted the seed will expect, and `Capability.deterministic` is reported `false` for GPU devices. Separately, the two sampler chains each hold their own `dist(seed)` (`:591`), so switching off the EOG-suppressing chain at token `min_new` restarts the RNG stream rather than continuing it.

**L-7.** From the delegated areas: hailo's `Session::budget` clamps `max_tokens` instead of refusing it and `session_create` never checks `max_batch` (unreachable through the core, reachable vtable-direct); a failed hailo write leaves the session half-written with a stale `n_rows`; `docs/packaging.md:49-50` claims a `.libs` exclusion that does not exist in the script (the property holds today, but by accident of the copy list); the archive README's own inventory omits `README.md` and `SHA256SUMS`; `Bundle::resolve()` returns the uncanonicalized path so integrity is hash-then-reopen; `manifest_sha256` is unreachable from the C ABI although `docs/bundles.md` calls it the thing to pin; Java handle `closed` flags are non-volatile and there is no `Cleaner`, so a dropped `Result` leaves its session permanently `BUSY`.

## Checked and found correct

Worth recording so these are not re-litigated.

**CUDA.** The `CudaSession` field order looks like a use-after-free (`model: Arc<ModelInner>` is declared first and so drops before `binding: IoBinding`) but is not: `ort::IoBinding` holds `_session: Arc<SharedSessionInner>` (`io_binding.rs:100-105`), so the `OrtSession` outlives the binding regardless. `drop(outputs)` is correctly placed after `self.stream.synchronize()` (`lib.rs:1197-1199`), so the ORT arena cannot recycle the output while a kernel is reading it. `copy_h2d` bound-checks against the destination; the three pinned staging sections are each `batch*seq*width` and the compaction writes `n_rows*used <= batch*seq`; `encode_row` cannot overflow a row (`budget <= seq`, `n_prefix <= budget-2`, `take <= budget-2-n_prefix`, final `col = 1+n_prefix+take+1 <= budget`); `aggregate_spans`' bound check is redundant but correct. Imported CUDA pointers are checked against the context's device ordinal; `preload_libraries` fails with the loader's own reason and never falls back to the CPU EP. The kernels are correct for the shapes they are launched with (block dim is always a power of two `<= 256`, the shared arrays are 256, `threads_for` is monotone, and the width-1 and all-masked-out edge cases behave). `CUDA_CAPS` honesty holds: `OPT_OUTPUT_DTYPE` and `DEVICE_TOKENIZE` are correctly absent and the matching options refused with `TURBO_E_UNSUPPORTED_OPTION`; `stage_placement` reports TokenClassify post-processing as `HOST`; embedding runs really do report `d2h_bytes == 0`.

**ggml.** The `LlamaContext<'static>` transmute is sound. `LlamaContext<'a>` holds `model: &'a LlamaModel` (`context.rs:26-34`) pointing into the `Arc<ModelInner>` heap allocation, and both `Generation` (`lib.rs:602-624`) and `EmbedSession` (`lib.rs:885-898`) declare `ctx` first and `inner` last. The grammar sampler also holds `model.vocab_ptr()` (`sampling.rs:300-320`) and `sampler`/`sampler_no_eog` are likewise declared before `inner`. `min_new_tokens` via a `-inf` EOG bias on a second chain is correct, and `self.sampler.accept(t)` keeps the two chains' grammar and penalty state in sync because `llama_sampler_sample` accepts into the chain it sampled from. `prefill`'s chunking sets the logits flag on the overall last token only, and `idx = batch.n_tokens() - 1` matches it in both the post-prefill and the steady-state case. `n_past`/`n_ctx` accounting cannot overrun the KV cache. `penalties(n_vocab, last_n, repeat, freq, present)` matches the crate's argument order. `GGML_CAPS` is honest where it matters most: `DEVICE_RESULT` is deliberately clear and `alloc` refuses every non-HOST placement, `OPT_POOLING_OVERRIDE` is clear and a pooling override is refused naming the field, `OPT_OUTPUT_DTYPE` is clear and non-F32 refused, `import` is refused. Nothing can unwind across the plugin boundary: `plugin_export::boundary` wraps every slot in `catch_unwind` and the workspace sets no `panic = "abort"`.

**Core and capi.** `turbo_generate`'s chunk pointers are valid for exactly the callback's duration (`drop(chunk)` at `capi/src/lib.rs:1568` is after the call), and callback re-entrancy into the same generation is structurally impossible because the generation handle is never exposed. `cancel()` on a finished generation is a no-op returning `Ok` (`handles.rs:923-929`), so `TURBO_STREAM_STOP` on the final chunk does not turn a complete generation into an error. `MAX_PLUGIN_OUTPUTS`/`MAX_PLUGIN_SPANS` are checked before any slice is formed, and the `n_outputs == 0 || outputs.is_null()` guard prevents `from_raw_parts(null, 0)`. The lease is now taken under the session lock in all six write paths and in `run`. The mock's sampling model is honest about being a model. Keeping provider libraries resident is a reasonable call, correctly documented at `plugin.rs:42-49`.

## Principles 1 through 8

**1. One contract.** Two breaks. H-1: the CUDA word-span port and the OpenVINO original disagree on the same input, so a caller gets different NER spans from the same bundle depending on the device. M-7: `turbo_provider_common.hpp` carries a second, laxer `struct_size` rule than `turbo-abi::Versioned`, and it is the rule the previous review reproduced a segfault against. Otherwise the header did its job this cycle — the CUDA, ggml, and Hailo providers all went in without a vendor-specific surface, and `turbo_generate` closed the last declared-but-unimplemented entry point.

**2. Honest capabilities.** The biggest improvement in the range and still the biggest source of findings. `b85ccf1` genuinely closed H7: every generation option now has a bit and a field index, `max_tokens` is refused rather than clamped everywhere, and output dtype is compared against `dtype_used` instead of hardcoded. What remains is options that are advertised and then not honored exactly: H-3 (stop strings truncated only within one chunk), M-1 (LEFT truncation ceiling), M-4 (the attention mask reinterpreted), M-5 (logprobs from the wrong distribution), M-6 (truncation assuming both-ended specials), plus the hailo clamps reachable vtable-direct.

**3. Lowest layer per device.** Held. CUDA pools, normalizes, and applies activations on the device from the model output and reports `d2h_bytes == 0` for embeddings, verified by its own test. ggml is honest in the opposite direction: pooling in the graph, L2 on the host, `DEVICE_RESULT` deliberately clear, placement `HOST`, and `d2h_bytes` counted — exactly the shape the principle asks for when a runtime will not hand back device memory. Hailo reports `fully_accelerated = 0` with the host stages named.

**4. Device policy.** Held. `AUTO` never selects a CPU; the ggml provider enumerates the ggml CPU device and documents that AUTO skips it; `cuda_lib_dir` failure is `device_unavailable`, never a CPU-EP fallback, and there is a test for it.

**5. Ownership is executable.** Held in the core and in Java (a `Result` read correctly after its `Session`, `Model`, `Context` and `Runtime` were all closed), and the provider-side drop order is enforced by field order in `handles.rs`, not by comment. Two gaps: Swift has no `close()` on `Runtime`/`Context`/`Model`/`Session`, so the conformance case that claims to test parent-release cannot (M-13), and Java's parent back-references are only partial, which is a trap for any future `Cleaner` (L-7).

**6. Per-model truth lives in the bundle.** The weakest area now, and it moved backwards relative to the H6 fix. H-7 (sparse `id2label` silently renumbered) puts a wrong label set into the contract. M-10 (`embedding_dimension` not read, `include_prompt` not read anywhere in the tree) means the cross-check the review closed H6 with does not fire on the schema the repository's own fixture uses. These are all in `tools/turbo-bundle/src/import.rs` and all fixable with guards.

**7. Measured, not claimed.** Mixed. Every new capability cell is `EXPERIMENTAL`, which is the honest state, and the receipts landed. But three measurement claims do not hold up: M-3 (`host_allocs: 0` is false and the suite's allocation assertion is vacuous for both new providers), M-8 (a quantized provider sets its own precision gate, so the cosine half of the live suite is self-certifying), M-9 (a measured floor published for a front end no receipt covers). M-11 also belongs here: an archive whose providers are never loaded is not a measured artifact.

**8. No one-offs.** Held. Nothing in the range adds a per-consumer function or flag; `turbo_generate` is the push form of the existing pull iterator, not a second path.
